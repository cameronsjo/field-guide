Anatomy of an architecture prompt

An architecture prompt that lands names the overall shape, how the parts talk, where the data lives, how it fails, and the one or two mistakes to steer clear of. Here is what that sounds like for five kinds of system. Tap any term to jump to its card.

  • State the limits firstTeam size, expected load, budget and how long it must live. "Three developers, 10k users, one Postgres" rules out half the patterns before you start.
  • Ask for the tradeoffEvery pattern here costs something. Asking Claude to name the cost of each choice, and what would make it change its mind, catches over-engineering early.
  • Name what to avoid"No distributed monolith, no shared database between services." Saying the failure out loud is often clearer than describing the success.
  • Point at the code shape too"Hexagonal, with ports in the domain package" or "vertical slices per feature" decides where every new file goes.

Problem to pattern

Start from the problem you actually have. Read across from the simplest thing that works, to what you reach for when it grows, to the mistake people usually make.
